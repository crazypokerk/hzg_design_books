PDA 页面顺不顺，很多时候不在布局，而在交互细节：扫码后有没有反馈，焦点会不会丢，回车会不会误提交，失败后能不能接着干。

## 扫码是主输入

仓储、物流、生产、巡检页面里，扫码不是普通输入框的附加功能，而是主流程入口。

推荐流程：

```text
进入页面
-> 自动聚焦扫码入口
-> 扫描条码
-> 立即显示码值或“校验中”
-> 校验成功后带出数据
-> 进入数量输入或准备下一次扫码
-> 校验失败时保留码值，显示原因和恢复动作
```

不要让用户每扫一次都先点输入框。

## 焦点规则要固定

连续作业最怕焦点丢失。用户扫了码页面没反应，现场通常会认为系统坏了。

| 场景 | 焦点应该在哪里 |
| --- | --- |
| 页面打开 | 扫码入口 |
| 扫库位成功 | 物料扫码入口 |
| 扫物料成功 | 数量输入框，或直接等待确认 |
| 数量回车确认后 | 提交中，禁用重复输入 |
| 提交成功 | 清空当前记录，回到扫码入口 |
| 提交失败 | 停在需要修改的字段 |
| 弹层关闭 | 回到打开弹层前的焦点 |

这些规则应该在页面说明里写清楚，不要交给开发临场猜。

## 回车只做一件事

很多扫描头会在条码后自动带回车。回车行为必须稳定。

- 扫码框回车：触发扫码校验。
- 数量框回车：数量有效时触发确认。
- 提交中回车：忽略，防止重复提交。
- 异常状态回车：回到安全动作，例如重新扫码。

同一个回车不要同时触发扫码和提交，也不要让表单默认跳转。

## 成功后自动继续

连续作业页成功后要自动准备下一条。

```text
确认收货成功
-> 最近记录新增一条
-> 已收数量更新
-> 清空当前物料和数量
-> 聚焦扫码入口
-> 提示“请扫描下一件物料”
```

不要让用户自己清空、自己点下一条。

## 失败后保留现场数据

失败时不要急着清空输入。用户需要核对刚才扫了什么、为什么失败。

```text
物料不属于当前收货单
当前码值：M-10086
可操作：重新扫码 / 上报异常
```

只弹“操作失败”然后清空输入，会让现场排查变得很难。

## 按钮要直接说动作

按钮文案用业务动作，不用泛词。

| 推荐 | 不推荐 |
| --- | --- |
| 确认收货 | 确定 |
| 确认盘点 | 提交 |
| 重新扫码 | 处理 |
| 稍后补传 | 下一步 |
| 上报异常 | 操作 |

同一阶段只保留一个最明显的主按钮。次要动作弱化或放到更多入口，危险动作单独确认。禁用按钮要说明原因。

## 数量录入要省事

数量输入是高频动作，别做成复杂表单。

- 使用数字键盘。
- 默认带出常用值，例如 `1`、账面数量、包装数量。
- 显示单位，例如 `PCS`、`kg`、`箱`。
- 输入时实时显示差异。
- 超范围时立即提示。
- 回车可以确认。

正常流程不要强制写长备注，异常时再补原因。

## 重复扫码要有规则

重复扫码不一定是错误，要看业务含义。

| 重复情况 | 处理建议 |
| --- | --- |
| 扫描头短时间重复触发 | 前端防抖，避免重复处理 |
| 同一物料已处理 | 提示已处理，允许查看记录 |
| 业务允许累计 | 合并数量并显示累计结果 |
| 业务允许覆盖 | 要求确认并记录原因 |
| 上一条结果不确定 | 先确认状态，避免重复提交 |

关键业务不要只靠禁用按钮防重复，服务端也要能识别重复提交。

## 错误提示要给下一步

错误提示按这个格式写就够：

```text
发生了什么 + 用户现在能做什么
```

示例：

```text
物料不属于当前收货单，请重新扫描物料码或上报异常。
```

```text
网络连接中断，当前记录已暂存，恢复后可补传。
```

```text
提交结果暂时无法确认，请刷新状态，不要重复扫描同一箱号。
```

## 检查清单

- 页面打开后是否自动聚焦扫码入口？
- 扫码后是否立即显示码值或处理状态？
- 回车行为是否唯一且稳定？
- 成功后是否自动准备下一条？
- 失败后是否保留码值、输入和恢复动作？
- 主按钮是否只有一个，文案是否说明具体业务动作？
- 重复扫码和重复提交是否有前后端规则？
