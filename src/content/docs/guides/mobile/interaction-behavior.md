## 核心问题

交互与行为不是给页面加几个点击效果，而是定义用户完成任务时每一步怎么发生：

- 用户现在能做什么
- 用户操作后，系统立刻给什么反馈
- 操作成功后，用户下一步去哪里
- 操作失败、中断或误操作后，用户怎么恢复

移动端的屏幕小、输入成本高、网络和设备环境更不稳定。只要交互规则没有设计清楚，页面就容易出现这些问题：按钮看得到但不知道能不能点，点了以后不知道有没有生效，失败后不知道怎么改，连续作业时需要反复确认和返回。

设计交互时，先把一次任务当成一条完整路径，而不是单独设计某个按钮或表单。

## 设计步骤

### 1. 先画行为路径

在设计按钮、表单和弹层之前，先写出用户完成任务的完整路径：

```text
进入页面 -> 判断当前状态 -> 执行主操作 -> 系统处理 -> 得到结果 -> 继续下一步 / 修正错误 / 返回
```

每一步都要明确三个点：

- 用户动作：用户要点击、输入、扫码、选择、上传还是确认
- 系统反馈：系统要展示加载、校验、成功、失败、禁用原因还是进度
- 下一步：成功后进入哪里，失败后停在哪里，中断后能不能继续

示例：

```text
仓管员进入收货页
-> 扫描物料码
-> 系统校验物料是否属于当前单据
-> 匹配成功后自动带出数量
-> 确认数量并确认收货
-> 成功后进入下一条
-> 失败时保留当前数据，并提示失败原因和处理动作
```

如果这条路径写不清，后面的按钮位置、表单顺序、反馈方式通常也会混乱。

### 2. 定义主操作和次操作

移动端每个页面都应该有一个清楚的主操作。主操作是用户完成当前任务最自然、最重要的下一步，不是页面上最想让用户点的按钮。

常见操作层级：

| 操作类型 | 使用场景 | 设计要求 |
| --- | --- | --- |
| 主操作 | 提交、确认、保存、继续扫码、同意审批 | 每个页面或每个任务区域最多一个，要直接说明动作 |
| 次操作 | 取消、返回、暂存、查看详情、切换方式 | 不能抢主操作视觉层级，位置和样式保持稳定 |
| 辅助操作 | 筛选、排序、展开、复制、刷新 | 可以放在工具栏、图标按钮或更多菜单中 |
| 危险操作 | 删除、作废、驳回、清空、撤销提交 | 必须说明后果，必要时二次确认或提供撤销 |

按钮文案使用动宾结构，让用户一眼知道点下去会发生什么：

- 🚨**推荐：“提交审批”、“确认收货”、“保存草稿”、“重新扫码”、“继续下一条”，清晰易懂；**
- 🚧不推荐：“确定”、“处理”、“操作”、“下一步”，这种有说明但不说明下一步是什么。

按钮尺寸建议：

- 常规按钮高度不小于 `44px`。
- `PDA` 高频按钮高度不小于 `48px`。
- 图标按钮点击热区不小于 `40px x 40px`。
- 相邻点击区之间至少保留 `8px` 间距，避免误触。

固定底部按钮适合提交、确认、继续等高频动作；页面内按钮适合局部编辑、展开、选择等局部动作。**不要把页面主操作藏进右上角、手势、长按或更多菜单里**。

### 3. 设计输入顺序和表单行为

表单不是字段集合，而是用户完成录入任务的路径。字段顺序要符合真实填写顺序，而不是数据库字段顺序。

表单设计先分三类字段：

| 字段类型 | 处理方式 |
| --- | --- |
| 必填且高频 | 靠前展示，默认可见，必要时自动聚焦 |
| 必填但低频 | 放在后续分组，提交前必须明确校验 |
| 选填或补充信息 | 后置、折叠或放到“更多信息”里 |

输入行为要提前定义：

- 标签放在输入框上方，不用占位符代替标签
- 数字、金额、电话、日期、邮箱等字段使用匹配的输入类型和键盘
- 有明确格式的字段给出示例，例如日期、批号、手机号、条码
- 能默认带出的值不要让用户重新输入
- 能选择的内容不要让用户自由输入，例如仓库、人员、状态、物料
- 输入法弹起后，当前字段和主要操作仍然要可见或可继续完成

校验方式按风险选择：

| 校验类型 | 适合时机 | 示例 |
| --- | --- | --- |
| 即时校验 | 格式明确、成本低的字段 | 手机号位数、金额格式、必填状态 |
| 离焦校验 | 需要用户输入完整后判断 | 编号长度、日期范围、数量上下限 |
| 提交校验 | 依赖多字段或服务端判断 | 库存是否足够、审批状态是否变化 |
| 阻断校验 | 继续操作会造成错误结果 | 物料不匹配、无权限、单据已关闭 |

提交失败后，必须保留已填内容，并把用户定位到第一个需要修正的字段。不要让用户重新从头录入。

### 4. 设计反馈和状态

用户操作后，需要知道“系统收到了没有、正在做什么、结果是什么”。用户做的操作越重要、影响越大、等待越久，系统反馈就应该越明显、越稳定、越能指导下一步。不能所有操作都只弹一个几秒钟就消失的 `Toast`。
> 不同操作需要不同强度的反馈。轻量操作可以用 `Toast`，但提交、上传、校验失败、权限不足等关键场景，需要在页面内展示明确状态、原因和下一步动作，不能只靠几秒后消失的提示。

常见反馈方式：

| 场景 | 推荐反馈 |
| --- | --- |
| 点击按钮后立即处理 | 按钮进入加载态或禁用态，并显示“提交中”、“保存中” |
| 局部内容刷新 | 当前区域展示骨架屏、加载文案或进度 |
| 长任务处理 | 展示进度、预计状态或可离开提示 |
| 操作成功且无需停留 | 短提示后自动进入下一步 |
| 操作成功但需要确认结果 | 页面内展示成功状态和下一步动作 |
| 轻微错误 | 字段下方或局部区域提示 |
| 关键错误 | 页面内错误区、弹层或阻断提示，并给出处理动作 |

`Toast` 只适合轻量、短暂、不影响后续操作的信息，例如“已复制”、“保存成功”。关键错误、不可操作原因、提交失败、权限不足不能只靠 `Toast`，因为用户可能错过提示，也不知道下一步怎么做。

页面至少要覆盖四类基础状态：

- 空状态：没有数据时说明原因，并给出可执行动作，例如“新建”、“重新筛选”、“刷新”
- 忙状态：加载、提交、扫码校验、上传处理中，要防止重复操作
- 错误状态：说明发生了什么、为什么影响任务、用户能怎么恢复
- 完成状态：告诉用户结果，并提供下一步，例如返回列表、继续下一条、查看详情

### 5. 设计错误恢复

错误提示的目标不是告诉用户“错了”，而是帮助用户把任务继续做完。

错误信息建议按这个结构写：

```text
发生了什么 + 为什么发生 / 有什么影响 + 用户现在可以怎么做
```

示例：

- 🚧不推荐：“提交失败”
- 🚨**推荐：“提交失败，当前单据已被他人审核。请刷新后查看最新状态。”**

- 🚧不推荐：“条码错误”
- 🚨**推荐：“物料不属于当前收货单，请重新扫码或切换收货单。”**

- 🚧不推荐：“网络异常”
- 🚨**推荐：“网络连接中断，已保留当前填写内容。恢复网络后可继续提交。”**

错误恢复要做到：

- 保留已输入、已选择、已上传的内容
- 定位到第一个错误字段或错误区域
- 告诉用户哪些内容需要修改，哪些内容已经成功
- 提供重试、重新扫码、刷新状态、保存草稿、联系管理员等具体动作
- 对重复提交、超时、弱网、断网要有明确处理策略

对于关键提交，建议支持防重复提交和幂等处理。用户连续点击、网络重试或页面恢复时，系统不应产生重复单据、重复审批或重复扣减。

### 6. 设计完成后的下一步

很多移动端页面只设计了“怎么提交”，没有设计“提交之后怎么办”。这会让用户在成功后停在原地，不知道任务是否结束。

需要明确：

- 成功后留在当前页，还是返回列表
- 是否刷新列表状态和数量
- 是否展示结果详情或提交记录
- 是否进入下一条任务
- 是否保留筛选、搜索和滚动位置
- 是否支持继续录入、继续扫码或再次提交同类任务

不同任务的成功路径不同：

| 任务类型 | 成功后的推荐行为 |
| --- | --- |
| 审批处理 | 返回待办列表，并更新当前单据状态 |
| 表单新建 | 展示成功结果，提供“查看详情”和“继续新建” |
| 收货/盘点 | 自动进入下一条或保持扫码焦点 |
| 异常上报 | 展示上报编号和后续处理入口 |
| 设置保存 | 留在当前页，明确提示已保存 |

成功反馈不能只写“操作成功”。要让用户知道任务是否已经结束，以及下一步最合理的动作是什么。

### 7. 单独设计 `PDA` 高频作业

`PDA` 页面通常用于仓库、门店、生产线等高频场景，核心目标是减少停顿和误操作。它可以复用手机端规则，但不能照搬手机端的慢流程。

`PDA` 交互优先考虑：

- 支持扫码枪输入、回车确认、`Tab` 切换和自动聚焦
- 扫码成功后自动进入下一字段或下一条，不要求用户额外点击
- 成功和失败要有明显反馈，必要时加入声音、震动或高对比提示
- 高频按钮更大，关键按钮位置固定，减少视线和手指移动
- 异常分支要短，能快速重新扫码、跳过、暂存或上报
- 弱网或离线场景要考虑本地暂存、队列、补传和失败重试

示例：

```text
扫描库位 -> 自动校验库位
-> 扫描物料 -> 自动校验物料
-> 输入数量 -> 回车确认
-> 成功后清空输入并聚焦下一次扫码
-> 失败后停留当前条，显示原因和“重新扫码 / 跳过 / 上报异常”
```

高频作业里，不要让用户每处理一条都经历“打开详情 -> 填写 -> 确认 -> 返回列表 -> 再打开下一条”。这种流程在桌面端还能接受，在 `PDA` 上会明显拖慢效率。

## 交互草图模板

设计或评审一个移动端页面时，可以按下面模板补齐行为规则：

```text
页面名称：
用户任务：

行为路径：
1. 进入页面后先判断：
2. 用户主操作：
3. 系统处理方式：
4. 成功后下一步：
5. 失败后恢复方式：

按钮规则：
- 主操作：
- 次操作：
- 危险操作：
- 禁用原因如何展示：

表单规则：
- 必填高频字段：
- 低频字段：
- 默认值：
- 输入类型：
- 校验时机：

反馈与状态：
- 加载状态：
- 空状态：
- 提交中状态：
- 成功状态：
- 错误状态：

返回与中断：
- 返回到哪里：
- 是否保留筛选和滚动位置：
- 是否保存草稿：
- 是否支持重试：
```

如果模板里的“成功后下一步”和“失败后恢复方式”填不出来，说明交互还没有设计完整。

## 示例：移动审批页

一个“请假审批”页面，不应该只放两个按钮“同意”和“驳回”。更完整的交互可以这样设计：

```text
进入页面：
- 展示申请人、请假类型、时间、时长、当前审批状态
- 展示异常提示，例如余额不足、时间冲突、已超期

主操作：
- 同意审批

次操作：
- 驳回
- 查看历史记录

提交前：
- 如果驳回，必须填写驳回原因
- 如果单据状态已变化，阻止提交并提示刷新

提交中：
- 按钮显示“提交中”，防止重复点击

成功后：
- 返回待办列表，当前单据从待办中移除
- 保留列表筛选和滚动位置

失败后：
- 保留审批意见
- 显示失败原因
- 提供“重试”或“刷新状态”
```

这样用户不只知道能点哪个按钮，也知道点完以后会发生什么，失败后该怎么继续。

## 示例：`PDA` 收货扫码页

`PDA` 收货页面的目标不是完整展示单据，而是让仓管员快速、连续、低错误地完成收货。

```text
首屏：
- 当前收货单号、供应商、已收/应收数量
- 当前扫描物料和校验状态
- 大号输入框或扫码焦点

主流程：
- 扫描物料码
- 系统校验是否属于当前收货单
- 成功后自动进入数量输入
- 输入数量后回车确认
- 成功后自动进入下一次扫码

异常流程：
- 物料不匹配：提示原因，提供“重新扫码 / 上报异常”
- 数量超出：提示可收数量，要求修正
- 网络中断：保留本地记录，提示稍后补传
```

这类页面要优先优化连续操作效率，而不是把所有单据字段都塞进首屏。

## 💡推荐做法

- 先写完整行为路径，再设计按钮、表单和反馈
- 每个页面或任务区域只保留一个明确主操作
- 按钮文案说明具体动作，不用含糊的“确定”、“处理”、“操作”
- 输入字段按真实填写顺序排列，必填高频字段优先
- 提交失败后保留内容，并定位到第一个错误点
- 关键错误在页面内展示原因和处理动作，不只依赖 `Toast`
- 成功后明确下一步，例如返回列表、继续下一条、查看详情
- `PDA` 高频场景支持扫码、回车、自动聚焦、连续处理和失败重试

## ❌不推荐做法

- 页面上放多个同样显眼的主按钮，让用户判断该点哪个
- 禁用按钮但不说明原因
- 用占位符代替字段标签
- 用户点击后没有任何即时反馈
- 提交失败后清空整张表单
- 只用 `Toast` 提示关键错误、权限不足或提交失败
- 把删除、作废、驳回等高风险操作藏在手势、长按或更多菜单里
- 把 `PDA` 连续作业做成普通手机表单，让用户反复确认和返回

## ✍️检查清单

- 用户进入页面后，是否知道当前能做什么？
- 主操作是否只有一个，且文案能说明具体动作？
- 点击、扫码、提交后，系统是否立刻给出反馈？
- 输入法弹起后，当前字段和关键操作是否仍然可用？
- 表单校验是否能帮助用户快速定位并修正错误？
- 禁用、失败、无权限、无数据时，是否说明原因和下一步？
- 提交中是否防止重复点击和重复提交？
- 成功后是否明确进入下一步或返回路径？
- 返回列表时，筛选条件和滚动位置是否能恢复？
- 断网、超时、中断后，用户是否能继续任务？
- `PDA` 场景是否支持扫码枪、回车、自动聚焦和连续处理？
