## 核心问题

性能不是上线前再补一轮优化，而是移动端页面能不能被正常使用的基础。

用户感知到的性能，通常不是某一个技术指标，而是这些体验：

- 页面能不能尽快打开？
- 首屏是否先展示当前任务最需要的信息？
- 点击、输入、扫码、筛选时是否有明显延迟？
- 列表滚动、图片加载、弹层打开是否稳定？
- 弱网、断网、超时后，任务能不能继续？
- 在旧手机、旧 `WebView`、`PDA` 上是否还能正常使用？

移动端性能设计的重点不是“把所有东西都做快”，而是先保证关键任务不断、关键操作可恢复、关键页面在真实设备上可用。

## 设计步骤

### 1. 先定义性能边界

在优化性能之前，先明确页面运行在哪些真实环境里。不同场景的性能风险完全不同。

需要先回答这些问题：

- 用户使用的是手机浏览器、企业微信/钉钉/飞书 `WebView`，还是 `PDA WebView`？
- 最小视口宽度是多少，是否需要覆盖 `240px`、`280px`、`320px` 的 `PDA`？
- 目标设备是新设备还是旧安卓、低内存设备、低性能 `PDA`？
- 使用场景是否存在弱网、断网、室外、仓库、生产线、扫码枪输入？
- 页面是偶尔查看，还是一天内高频连续操作？

示例：

```text
页面：PDA 盘点页
设备：PDA WebView，最小宽度 280px
场景：仓库内连续扫码，网络不稳定
核心性能目标：
- 扫码后 1 秒内给出匹配结果
- 断网时保留本地记录
- 网络恢复后支持补传
- 连续处理 200 条数据不卡顿
```

如果性能边界没有定义清楚，就容易只在桌面浏览器里看起来正常，到了真机、旧 `WebView` 或弱网环境就出问题。

### 2. 控制首屏内容

首屏性能的目标不是一次性展示完整信息，而是让用户尽快完成第一次判断。

首屏只优先加载这些内容：

- 当前任务必须识别的对象，例如订单号、物料、客户、人员、设备
- 当前状态，例如待处理、已完成、异常、超时、审核中
- 关键数值，例如数量、金额、时间、进度、差异
- 风险和限制，例如不可提交原因、异常原因、权限限制
- 当前主操作，例如确认、提交、继续扫码、处理异常

这些内容可以延后加载：

- 历史记录、日志、审批轨迹。
- 大量明细、附件、图片、长备注。
- 低频辅助字段。
- 非当前任务必需的统计、推荐、扩展信息。

首屏设计可以按这个顺序处理：

```text
先显示页面骨架
-> 加载核心信息
-> 允许用户完成首屏判断
-> 再加载明细、历史、附件等低优先级内容
```

不要为了“信息完整”在首屏一次性请求全量数据。移动端用户更需要先知道“当前能不能处理”，而不是先等待完整资料全部加载。

### 3. 拆分数据加载

性能问题经常不是页面写得慢，而是数据拿得太多、太早、太散。

常见数据加载策略：

| 数据类型 | 推荐策略 |
| --- | --- |
| 首屏核心数据 | 页面进入后优先请求，字段尽量精简 |
| 明细列表 | 分页、分批加载或按需展开 |
| 历史记录 | 进入对应区域后再加载 |
| 附件和图片 | 缩略图优先，原图按需查看 |
| 字典和配置 | 可缓存，避免每次重复请求 |
| 搜索结果 | 输入防抖，分页返回，避免一次返回过多 |

设计接口和页面时，要区分“首屏必须”和“稍后查看”：

- 首屏接口不要返回整张单据的全部字段
- 列表接口不要返回详情页才需要的大字段
- 明细数量较多时，不要一次性渲染全部行
- 字典、权限、用户信息等稳定数据可以缓存
- 页面返回时，尽量复用已有筛选条件、列表数据和滚动位置

如果一个页面打开慢，先检查是不是“首屏拉了全量数据”。这比盲目压缩代码、换动画、调样式更常见。

### 4. 处理长列表和复杂表格

移动端长列表的风险主要有三个：请求慢、渲染慢、滚动卡。

长列表优先使用这些方式：

- 分页加载：适合查询、审批、订单、任务列表
- 分批渲染：适合数据量中等但首屏不需要全部出现的列表
- 虚拟滚动：适合几百行以上且需要连续浏览的列表
- 搜索和筛选前置：先缩小结果范围，再展示列表
- 返回恢复：从详情返回列表时保留筛选条件和滚动位置

列表项要控制信息密度：

- 列表只展示判断和筛选需要的信息
- 复杂明细放到详情页或展开区域
- 不要把桌面端多列表格直接压缩到手机屏幕
- 金额、数量、状态、时间等关键字段要稳定显示

复杂表格在手机上通常不适合原样搬运。可以改成卡片式摘要、分组明细、横向少列展示或按字段详情展开。性能和可读性要一起考虑。

### 5. 管理图片、附件和媒体

图片和附件是移动端性能问题的高发来源。很多页面慢，不是因为业务复杂，而是因为图片太大、数量太多、加载太早。

推荐做法：

- 图片应按页面实际显示大小生成缩略图或压缩图，不要加载几MB的原图后再用CSS强行缩小显示
> 比如用户上传了一张手机照片：
> - 原图大小：4000 x 3000
> - 文件大小：8MB
> - 页面实际只显示成 120 x 90
> 如果直接加载这张8MB原图，然后用CSS改变大小：
> ```css
> img {
>    width: 120px;
>    height: 90px; 
> }
- 首屏图片优先加载，非首屏图片懒加载
- 列表中使用缩略图，查看时再加载大图
- 多图上传时显示压缩、上传中、失败和重试状态
- 附件只展示文件名、大小、类型和状态，点击后再下载或预览
- 对弱网环境，允许用户稍后上传、重新上传或补传

上传场景要特别设计失败恢复：

```text
选择文件 -> 本地展示待上传
-> 上传中显示进度
-> 成功后显示已上传
-> 失败后保留文件，并提供重试 / 删除 / 稍后上传
```

不要在用户提交失败后清空已选图片或附件。对用户来说，重新选择、拍照、上传的成本很高。

### 6. 保证交互响应

性能不只是打开速度，也包括用户操作后的响应速度。用户点击、输入、扫码之后，如果页面没有反馈，就会以为没有点中或系统卡住了。

常见交互响应要求：

| 场景 | 设计要求 |
| --- | --- |
| 点击提交 | 立即进入提交中状态，防止重复点击 |
| 搜索输入 | 使用防抖，停止输入后再请求 |
| 筛选切换 | 避免每点一次都全量刷新，可以合并请求 |
| 远程校验 | 显示校验中状态，不阻塞其他无关输入 |
| 连续扫码 | 扫码后快速反馈成功/失败，并自动准备下一次输入 |
| 弹层打开 | 避免打开时再同步加载大量内容 |

防抖和节流的含义可以简单理解为：

- 防抖：用户连续输入时先不请求，停下来一小段时间后再请求。适合搜索联想、远程校验。
- 节流：高频触发时控制执行频率。适合滚动加载、窗口变化、连续事件。

不要把所有请求都绑定在用户每一次输入、每一次点击、每一次滚动上。移动端网络和设备性能更容易被高频请求拖慢。

### 7. 设计弱网、断网和超时恢复

真实移动端环境里，网络失败不是异常小概率，而是必须设计的基础场景。

至少要覆盖这些情况：

- 接口超时。
- 网络断开。
- 请求失败但本地内容还在。
- 提交成功但前端没有收到结果。
- 上传中断。
- 离线作业后需要补传。

弱网恢复要做到：

- 告诉用户当前发生了什么，例如“网络连接中断”。
- 告诉用户任务是否受影响，例如“已填写内容已保留”。
- 给出可执行动作，例如“重试”、“保存草稿”、“稍后补传”、“刷新状态”。
- 关键提交要防重复提交，避免用户重试后产生重复数据。
- 对 `PDA` 高频作业，必要时支持本地队列和补传结果查看。

错误提示示例：

- 🚧不推荐：“请求失败”
- 🚨**推荐：“网络超时，当前填写内容已保留。请检查网络后重试。”**

- 🚧不推荐：“上传失败”
- 🚨**推荐：“图片上传失败，已保留本地文件。你可以重新上传或稍后补传。”**

- 🚧不推荐：“提交异常”
- 🚨**推荐：“提交结果暂时无法确认，请刷新状态，不要重复提交。”**

弱网设计的核心不是让失败消失，而是让用户知道任务有没有丢、能不能继续、下一步该做什么。

### 8. 单独验证 `PDA` 和旧 `WebView`

`PDA`、旧安卓和企业应用 `WebView` 的性能表现，不能只靠桌面浏览器模拟器判断。

这些场景需要真机验证：

- `PDA` 连续扫码、自动聚焦、回车确认
- 长时间打开页面后是否变慢
- 连续处理大量数据后是否卡顿
- 输入法弹起、收起后布局是否稳定
- 弱网、断网、恢复网络后的提交和补传
- 企业微信、钉钉、飞书、`App WebView` 中的兼容表现
- 低端安卓设备上的滚动、弹层、图片预览和上传

真机验证要尽量使用接近真实的数据量：

- 列表不要只测 5 条，要测 100 条、500 条或真实最大量级
- 图片不要只测小图，要测用户实际会上传的照片
- 扫码不要只测一次，要测连续几十次或几百次
- 网络不要只测满速环境，要测弱网、断网、恢复

模拟器只能帮助早期发现布局问题，不能替代真实设备的性能验证。

## 示例：移动订单列表页

一个订单列表页不要一次性加载全部订单和全部明细，可以这样设计：

```text
首屏：
- 加载筛选条件、订单摘要列表、当前状态数量
- 每条订单只展示订单号、客户、状态、金额、交付时间、异常标识

数据加载：
- 每页 20 条
- 下拉刷新当前筛选结果
- 上拉加载下一页
- 进入详情后再加载商品明细、物流、历史记录

交互响应：
- 搜索输入防抖
- 筛选变化后显示加载状态
- 返回列表时保留筛选和滚动位置

弱网恢复：
- 加载失败时保留已有列表
- 显示“刷新重试”
- 不清空用户输入的搜索条件
```

这样用户能先看到可判断的订单摘要，再按需进入详情，而不是等待所有订单明细全部加载完成。

## 示例：`PDA` 离线盘点页

`PDA` 盘点页的性能重点不是页面动画，而是连续扫码不中断、弱网不丢数据、恢复后能补传。

```text
首屏：
- 当前盘点任务、库位、已盘 / 应盘数量
- 扫码输入焦点
- 最近一次扫码结果

连续作业：
- 扫码后立即本地记录
- 本地校验物料格式和重复状态
- 网络可用时后台上传
- 上传失败进入待补传队列

反馈：
- 成功：显示物料名称和数量，并自动准备下一次扫码
- 失败：停留当前记录，显示原因和处理动作
- 离线：提示“离线记录中”，不阻断继续扫码

恢复：
- 网络恢复后自动补传
- 补传失败可手动重试
- 用户可查看待补传数量和失败原因
```

这种页面要优先保证连续作业稳定，而不是依赖每次扫码后都等待服务器返回。

## 💡推荐做法

- 先定义目标设备、网络环境、数据量和最低可用标准
- 首屏只加载当前任务必须判断的信息
- 明细、历史、附件、图片等低频内容延后加载
- 长列表使用分页、分批渲染或虚拟滚动
- 图片按显示尺寸输出，列表使用缩略图
- 搜索、筛选、远程校验使用防抖或节流
- 提交、上传、扫码等关键操作要有即时反馈和失败恢复
- 弱网、断网、超时场景要保留用户数据，并提供重试或补传
- `PDA` 和旧 `WebView` 必须用真机和真实数据量验证

## ❌不推荐做法

- 首屏一次性请求全量数据、全部明细、历史记录和附件
- 把桌面端复杂表格直接压缩到手机页面里
- 列表一次性渲染几百条甚至几千条数据
- 原图直接展示在列表或首屏中
- 用户每输入一个字、每切换一个条件就立刻发请求
- 网络失败后清空页面、清空表单或要求用户从头录入
- 只在桌面浏览器模拟器里验证性能
- 用大量动画、阴影、滤镜和复杂布局掩盖核心任务加载慢的问题

## ✍️检查清单

- 是否明确了目标设备、目标 `WebView` 和最小验证宽度？
- 首屏是否只加载当前任务必须的信息？
- 是否区分了首屏数据、明细数据、历史记录和附件？
- 列表是否有分页、分批渲染或虚拟滚动策略？
- 搜索、筛选、远程校验是否避免高频请求？
- 图片和附件是否使用缩略图、懒加载和失败重试？
- 点击、提交、上传、扫码后是否有即时反馈？
- 断网、超时、接口失败后，用户数据是否保留？
- 关键提交是否防止重复提交和重复扣减？
- 从详情返回列表时，筛选条件和滚动位置是否恢复？
- 是否使用真实设备、真实数据量和弱网环境验证通过？
