PDA 页面设计的第一步不是画界面，也不是列字段，而是先说清楚：这个页面到底帮现场人员完成哪件事。

如果这一步含糊，页面很容易变成“字段很多、按钮很多、功能看起来完整”，但用户拿到 PDA 后不知道先扫哪里、错了怎么改、成功后下一步去哪。

## 写一句页面任务

每个 PDA 页面都应该能用一句话讲清：

```text
谁在什么现场，为了完成什么任务，需要先判断什么，再做什么动作。
```

好的写法：

```text
仓管员在收货现场使用 PDA 扫描物料，为了完成当前收货单入库，
需要先判断物料是否属于当前收货单，再确认数量，成功后继续扫下一条。
```

不够好的写法：

```text
展示收货单信息，支持收货操作。
```

后者没有说明用户、现场、判断条件和成功后的流向，做页面时就容易把所有字段都堆上去。

## 现场条件要先定

同样是“扫码入库”，办公室测试和仓库现场是两回事。设计前先确认这些条件：

| 条件 | 影响 |
| --- | --- |
| 使用角色 | 仓管员、生产人员、巡检员的操作节奏不同 |
| 作业地点 | 光线、噪声、网络、是否戴手套都会影响交互 |
| 设备型号 | 屏幕宽度、扫描头、WebView、系统权限可能不同 |
| 是否使用 HAC | 决定能否调用扫码、定位、离线存储等能力 |
| 输入方式 | 扫描头、摄像头扫码、物理按键、触屏的流程不同 |
| 作业频率 | 偶尔查一次和连续扫几百条，页面结构不应一样 |

## 先分页面类型

不要把所有 PDA 页面都做成“列表 + 详情 + 表单”。先判断它属于哪类：

| 页面类型 | 适合场景 | 设计重点 |
| --- | --- | --- |
| 连续作业页 | 收货、盘点、复核、报工 | 扫码快、焦点稳、成功后下一条 |
| 任务选择页 | 选择盘点单、拣货任务、巡检路线 | 状态清楚、少筛选、快速进入任务 |
| 异常处理页 | 数量差异、破损、物料不匹配 | 原因明确、保留现场数据、能恢复或上报 |
| 查询页 | 查记录、查库存、查历史 | 可筛选、可分页，不抢主流程 |

很多业务会组合使用：

```text
任务选择页 -> 连续作业页 -> 异常处理页 / 查询页
```

## 主流程要短

连续作业页的流程越短越好。能在当前页完成的，不要让用户反复进出列表和详情。

推荐：

```text
进入任务 -> 扫码 -> 校验 -> 输入数量 -> 确认 -> 准备下一条
```

不推荐：

```text
进入列表 -> 打开详情 -> 扫码 -> 填表 -> 弹窗确认 -> 返回列表 -> 再打开下一条
```

后一种流程每条记录都打断一次，几十条以后差异会非常明显。

## 异常流程也要写出来

现场一定会遇到异常。页面设计时不要只画成功路径。

| 异常 | 页面应该支持 |
| --- | --- |
| 扫错码 | 保留码值，允许重新扫码 |
| 物料不匹配 | 显示原因，允许重扫或上报异常 |
| 数量超范围 | 停在数量输入，提示允许范围 |
| 重复扫码 | 判断是防抖、累计、覆盖还是查看记录 |
| 网络断开 | 本地暂存，显示待补传数量 |
| 提交结果不确定 | 保留记录，刷新状态，不鼓励盲目重提 |

异常流程的重点不是“提示失败”，而是让用户知道现在能做什么。

## 设计产出至少包含

开始开发前，页面说明里至少写清：

- 页面名称和页面类型
- 使用角色、现场、设备、是否使用 HAC
- 主要输入方式和默认焦点
- 一句话任务
- 主流程和异常流程
- 成功后的下一步
- 真机验收方式

这几项写清楚后，设计、实施和开发对页面边界会更一致。

## 检查清单

- 是否能用一句话说清页面任务？
- 是否确认真实 PDA、网络、扫码方式和 HAC 环境？
- 页面类型是否明确，不把主流程塞进查询页？
- 主流程是否避免反复进出详情页？
- 异常时是否保留现场数据并给出恢复动作？
- 是否定义了目标 PDA 上的验收方式？
