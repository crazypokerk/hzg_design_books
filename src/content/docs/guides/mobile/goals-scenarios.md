## 适用范围

适用于手机浏览器、企业微信/钉钉/飞书 `WebView`、`App` 内嵌 `H5`，以及 `PDA` 浏览器和 `PDA WebView`。

## 核心问题

移动端页面设计的第一步不是画界面，而是明确这页要解决什么任务、在哪种场景下使用、由谁使用、在什么设备上使用，交付标准是什么。

## 设计原则

- 页面目标要围绕任务完成，而不是围绕信息展示
- 同一业务在手机和 `PDA` 上可以共用规则，但不应强行共用完全相同的交互
- 先定义主流程，再定义异常流程和中断恢复
- 先明确设备边界，再定义界面结构和交互细节

## 设计步骤

### 1. 先定义用户和使用场景

移动端页面不是给“所有人”使用的。不同用户、场景和设备，会直接影响页面结构、交互方式和性能要求。

先回答这些问题：

- 谁在使用：审批人、仓管员、销售、巡检人员、门店人员，还是管理者？
- 在哪里使用：办公室、仓库、门店、生产线、户外，还是移动途中？
- 使用时是否紧急：是偶尔查看，还是需要连续高频处理？
- 使用时是否受环境影响：弱网、断网、强光、戴手套、单手操作、扫码枪输入？
- 用户最怕什么：录错、漏处理、找不到异常、重复提交，还是任务中断？

示例：

```text
用户：仓管员
场景：仓库收货现场
设备：PDA
特点：连续扫码、网络不稳定、需要快速处理异常
设计重点：减少点击、明确扫码结果、支持失败重试和补传
```

如果用户和场景没有定义清楚，后面很容易把手机审批页、仓库 `PDA` 作业页和管理查询页做成同一种结构。

### 2. 再写页面任务句

在画页面之前，先用一句话说明这个页面到底要帮用户完成什么任务。

可以使用这个句式：

> 用户在什么场景下，为了完成什么目标，需要先判断什么，再执行什么操作。

示例：

- 审批人在手机上查看报销单，需要判断费用是否合理，然后同意或驳回
- 仓管员在收货现场使用 `PDA` 扫码，需要确认物料是否匹配，并快速完成收货
- 巡检人员在现场使用手机拍照上报异常，需要记录问题、上传证据，并提交处理

任务句写清楚后，页面才知道该突出什么信息、放什么操作、支持什么异常恢复。

### 3. 明确主流程、异常流程和中断恢复

只定义正常流程是不够的。移动端真实使用环境里，失败、中断、状态变化很常见。

需要至少补齐三条路径：

| 路径 | 要回答的问题 |
| --- | --- |
| 主流程 | 用户正常完成任务时，每一步怎么走？ |
| 异常流程 | 校验失败、无权限、数据变化、扫码失败时怎么办？ |
| 中断恢复 | 断网、退出页面、提交失败、上传失败后如何继续？ |

示例：

```text
主流程：
扫码物料 -> 校验匹配 -> 输入数量 -> 确认收货 -> 进入下一条

异常流程：
物料不匹配 -> 显示原因 -> 重新扫码 / 上报异常

中断恢复：
网络断开 -> 保留已扫记录 -> 网络恢复后补传
```

如果异常流程和中断恢复没有定义，页面通常会在失败时只给一句“操作失败”，用户不知道下一步该怎么办。

### 4. 定义任务成功标准

页面做完不等于任务成功。设计开始前要定义“怎样才算这个页面真的可用”。

常见成功标准：

- 用户能在首屏判断当前状态
- 用户能找到主操作，并理解点击后会发生什么
- 用户能在失败后继续任务，不需要从头录入
- 用户能在目标设备上完成主要流程
- 高频作业能连续处理，不需要反复返回和确认
- 弱网、断网、超时后不会丢失关键数据

示例：

```text
页面：移动审批详情页
成功标准：
- 审批人能在首屏看到申请人、金额、原因、异常提示
- 审批人能明确同意或驳回
- 驳回时必须填写原因
- 提交失败后保留审批意见
- 返回待办列表时，列表状态更新且位置保留
```

成功标准越具体，后面的信息架构、交互、视觉和性能才越容易评审。

### 5. 判断手机和 `PDA` 是否需要不同体验

同一业务可以同时支持手机和 `PDA`，但不代表两个端要使用完全相同的页面。

可以按下面方式判断：

| 判断项 | 更适合手机 | 更适合 `PDA` |
| --- | --- | --- |
| 使用频率 | 偶尔查看、审批、查询 | 高频扫码、连续录入、现场作业 |
| 输入方式 | 触屏、键盘、拍照 | 扫码枪、回车、物理按键、触屏 |
| 页面重点 | 判断信息、处理决策 | 快速反馈、自动聚焦、连续处理 |
| 异常处理 | 查看原因后处理 | 快速重扫、跳过、暂存、补传 |

如果一个流程在 `PDA` 上需要连续处理，就不要照搬手机端“列表 -> 详情 -> 提交 -> 返回列表”的慢流程。反过来，如果手机端主要用于审批判断，也不需要强行做成扫码作业式界面。

## 页面大小

在设计开始前，我们需要先确认最终使用终端设备的页面大小。因此可以先用最终使用的终端移动设备访问来测试设备的显示区域具体信息，在此之前，可以先说明解释一下涉及到具体的页面参数。

> 1. `window.innerWidth`
>
>    浏览器**视口的宽度**，单位是CSS像素，代表用户实际可见的页面内容区域的**宽度**（不包括浏览器工具栏、地址栏等，但包括滚动条）。
>
> 2. `window.innerHeight`
>
>    浏览器**视口的高度**，单位 CSS 像素，代表用户实际可见的页面内容区域的**高度**（不包括浏览器工具栏、地址栏等，但包括滚动条）。
>
> 3. `window.devicePixelRatio`
>
>    物理像素与CSS像素的比值。
>
> 4. `screen.width`
>
>    设备**整个屏幕的宽度**，单位CSS像素（不是物理像素），表示屏幕的总逻辑宽度，包括系统状态栏、浏览器 UI 等所有区域。
>
> 5. `screen.height`
>
>    设备**整个屏幕的高度**，单位CSS像素（不是物理像素），表示屏幕的总逻辑高度，包括系统状态栏、浏览器 UI 等所有区域。

假设你在手机上竖屏观看，从外到内各层的关系如下： 

![area_relation](../../../../assets/area_relation.png)

> 视口测试网站：[viewportsizer](https://viewportsizer.com/)

📍记住一个关键点：设计布局时优先使用`window.innerWidth/innerHeight`（用户真正看到的区域），而判断设备硬件规格时使用 `screen` 系列 + `dpr`。两者不可混淆，否则容易出现内容被遮挡或留白过多的问题。

## 目标与场景模板

开始设计或评审一个移动端页面前，可以先把下面内容补齐：

```text
页面名称：
主要用户：
使用场景：
使用设备：

核心任务：
- 用户要完成什么：
- 用户先判断什么：
- 用户下一步做什么：

设备边界：
- 手机 / PDA / WebView：
- 最小视口宽度：
- 是否有输入法遮挡：
- 是否有扫码枪、拍照、上传、定位：

主流程：
1.
2.
3.

异常流程：
- 数据校验失败：
- 无权限 / 不可操作：
- 状态已变化：

中断恢复：
- 提交失败：
- 网络断开：
- 退出后返回：

任务成功标准：
- 首屏能判断：
- 主操作明确：
- 失败可恢复：
- 真机验证通过：
```

如果“核心任务”和“任务成功标准”填不出来，说明页面目标还不够清楚，不适合直接进入界面设计。

## 示例：移动审批页

```text
页面名称：报销审批详情
主要用户：审批人
使用场景：手机上处理待办审批
使用设备：手机浏览器或企业微信 WebView

核心任务：
- 判断这笔报销是否合理
- 查看金额、申请人、费用类型、附件和异常提示
- 同意或驳回

主流程：
进入审批页 -> 查看关键信息 -> 填写审批意见 -> 同意 / 驳回 -> 返回待办列表

异常流程：
- 单据已被他人处理：提示状态变化，刷新最新状态
- 驳回原因未填写：定位到原因输入框

任务成功标准：
- 首屏能看到申请人、金额、费用类型、当前状态
- 主操作明确
- 提交失败后保留审批意见
- 返回待办列表时状态更新
```

这个页面的重点是帮助审批人快速判断和决策，不需要把所有历史记录和低频字段都放到首屏。

## 示例：`PDA` 收货页

```text
页面名称：PDA 收货扫码
主要用户：仓管员
使用场景：仓库收货现场连续扫码
使用设备：PDA WebView

核心任务：
- 扫描物料
- 判断物料是否属于当前收货单
- 确认数量并进入下一条

主流程：
扫描物料 -> 系统校验 -> 确认数量 -> 收货成功 -> 自动准备下一次扫码

异常流程：
- 物料不匹配：提示原因，支持重新扫码或上报异常
- 数量超出：提示可收数量，要求修正

中断恢复：
- 网络断开：保留本地记录
- 上传失败：进入待补传队列

任务成功标准：
- 扫码后能快速看到成功或失败结果
- 成功后自动准备下一次扫码
- 失败后不清空当前记录
- 弱网时不丢失已扫数据
```

这个页面的重点是连续作业效率和失败恢复，不适合照搬手机端审批或详情页结构。

## 💡推荐做法

- 先定义用户、场景、设备和核心任务，再画页面
- 用一句任务句说明页面目标，避免页面变成字段堆叠
- 同时设计主流程、异常流程和中断恢复
- 明确任务成功标准，用它来评审后续设计
- 先确认 `window.innerWidth/innerHeight`，再决定布局和固定区域
- 手机和 `PDA` 可以复用业务规则，但要按使用频率和输入方式决定是否拆分交互

## ❌不推荐做法

- 还没定义用户和场景，就直接开始画页面
- 只描述“展示某某信息”，不说明用户要完成什么任务
- 只设计正常流程，不考虑失败、断网、退出和恢复
- 强行让手机和 `PDA` 使用完全相同的交互
- 只按设计稿宽度判断页面，不用真实设备查看视口
- 把 `screen.width/height` 当成用户真实可见的页面区域

## ✍️检查清单

- 是否明确主要用户是谁？
- 是否明确页面在哪种场景下使用？
- 是否写出一句清楚的页面任务句？
- 是否区分主流程、异常流程和中断恢复？
- 是否定义了任务成功标准？
- 是否明确手机、`PDA`、`WebView` 的设备边界？
- 是否确认真实可见区域使用 `window.innerWidth/innerHeight`？
- 手机和 `PDA` 是否需要不同交互，而不是强行共用？
