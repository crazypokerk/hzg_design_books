## 核心问题

信息架构不是把字段排进页面，而是把用户完成任务所需的信息、判断和操作排成一条清楚的路径。

做移动端页面时，先回答三个问题：

- 用户打开这个页面时，最想判断什么？
- 判断之后，用户最可能做什么操作？
- 如果信息很多，哪些必须现在看到，哪些可以稍后展开？

只要这三个问题没有回答清楚，页面就容易变成“字段都在，但用户不知道下一步做什么”。

## 设计步骤

### 1. 先写任务句

在画页面之前，先用一句话定义页面任务：

> 用户在什么场景下，为了完成什么目标，需要先判断什么，再执行什么操作。

示例：

- 仓管员在收货现场，需要确认这批货是否可入库，并快速处理数量异常
- 审批人在手机上查看请假单，需要判断申请是否合理，然后同意或驳回
- 盘点人员使用 `PDA` 连续扫码，需要知道当前物料是否匹配，并自动进入下一条

这句话会决定页面结构。如果任务句写不清，信息分组和操作优先级通常也会混乱。

### 2. 再定首屏重点

首屏只解决一个问题：让用户快速完成第一次判断。

优先放这些信息：

- 对象：订单号、物料、客户、人员、仓库、设备等
- 状态：待处理、已完成、异常、超时、审核中等
- 关键数值：数量、金额、时间、差异、进度等
- 风险提示：异常原因、限制条件、不可操作原因等
- 主操作：当前最自然的下一步，例如“确认收货”“提交审批”“继续扫码”

首屏不适合放大量说明文字、完整字段清单或低频辅助信息。用户还没完成判断前，不要先让用户读完整份资料。

### 3. 按任务顺序分组

信息分组要符合用户处理事情的顺序，而不是数据库字段顺序。

常见分组方式：

- 基础信息：识别对象，帮助用户确认自己看的是不是这一条
- 任务信息：本次要处理的数量、状态、要求、截止时间
- 异常信息：差异、失败原因、风险提示、处理建议
- 操作信息：可执行动作、限制条件、提交结果
- 历史记录：处理轨迹、审批记录、日志、备注

如果一个分组里字段很多，继续拆成“必须判断”和“补充查看”。必须判断的信息直接展示，补充信息用折叠、详情展开或标签页承载。

### 4. 选择页面结构

不同任务适合不同结构，不要所有页面都做成冗长的详情页。

| 任务类型 | 适合结构 | 设计重点 |
| --- | --- | --- |
| 快速确认 | 单页任务 | 首屏给出结论信息和主操作 |
| 查询处理 | 列表到详情 | 列表帮助筛选和比较，详情帮助判断和处理 |
| 复杂录入 | 分步任务 | 每一步只处理一类信息，并显示进度 |
| 高频作业 | 连续作业 | 支持扫码、自动跳转、成功/失败即时反馈 |
| 异常处理 | 主流程加异常分支 | 告诉用户原因、影响和可恢复动作 |

页面结构选错后，再优化视觉和交互也很难补救。例如，把连续扫码做成普通表单，会让用户不断确认、返回、再进入下一条，效率会很低。

### 5. 设计返回和恢复

移动端页面层级越深，用户越容易丢失上下文。设计页面时要同时设计“怎么进去”和“怎么回来”。

需要明确：

- 从列表进入详情后，返回列表是否保留筛选条件
- 返回列表时，滚动位置是否恢复到刚才那一条
- 分步流程中断后，是否能继续上次进度
- 提交失败后，已填内容是否保留
- 深层详情页是否有明确返回入口，而不是只依赖浏览器返回

## 页面草图模板

设计一个移动端页面时，可以按下面顺序整理内容：

```text
页面名称：
用户任务：

首屏判断：
- 对象：
- 状态：
- 关键数值：
- 风险提示：
- 主操作：

内容分组：
1. 基础信息：
2. 任务信息：
3. 异常信息：
4. 历史记录：

页面结构：
- 单页任务 / 列表到详情 / 分步任务 / 连续作业

返回与恢复：
- 返回到哪里：
- 是否保留筛选：
- 是否恢复滚动位置：
- 失败后如何恢复：
```

如果填不出“首屏判断”和“主操作”，说明页面目标还不够清楚，需要回到目标与场景重新确认。

## 示例：订单详情页

一个“订单详情”页面不要一上来平铺所有字段，可以这样组织：

```text
首屏：
- 订单号、客户名称、当前状态
- 应收金额、交付时间、异常提示
- 主操作：确认发货 / 处理异常

基础信息：
- 客户、联系人、地址、备注

商品信息：
- 商品列表、数量、单价、小计

任务信息：
- 仓库、物流、发货时间、签收状态

历史记录：
- 创建、修改、审核、发货、异常处理记录
```

这样用户就能先判断“这张订单现在能不能处理”，再决定是否查看商品、物流或历史细节。

## 💡推荐做法

- 页面标题明确对象和任务，例如“订单详情”、“库存盘点”、“异常上报”
- 首屏展示状态、数量、金额、时间、异常提示等关键判断信息
- 字段、模块和操作按用户实际处理顺序排列
- 长内容用分组、折叠、标签页或详情展开，避免首屏堆叠
- 列表进入详情再返回列表时，保留筛选条件和滚动位置
- 复杂流程展示当前步骤、完成进度和下一步动作

## ❌不推荐做法

- 首屏放**大量说明文字**或营销式内容
- 把所有字段平铺在一个长页面里
- **直接沿用桌面端**复杂多列布局
- 页面分组按数据库表结构命名，例如“主表信息”、“子表信息”
- 让用户依赖浏览器返回在多层页面里找位置
- 把异常、失败、不可操作原因藏在页面底部

## ✍️检查清单

- 用户打开页面后，是否能在首屏判断当前状态
- 主操作是否和用户下一步任务一致
- 信息分组是否符合真实处理顺序
- 低频信息是否被合理后置或折叠
- 页面层级是否过深，返回路径是否明确
- 从列表、流程或异常状态返回时，是否能恢复上下文
