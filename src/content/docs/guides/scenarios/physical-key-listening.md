## 功能介绍

物理按键监听用于在 `HAC` 中接收 Android 设备或 PDA 上的实体按键事件，并在用户按下指定按键时执行对应的子命令。

这类能力适合把高频动作从触屏操作转移到设备按键上，例如确认、提交、返回当前步骤、触发扫码前置逻辑、切换数量、打开异常登记等。对于戴手套、单手握持、强光环境或连续作业场景，物理按键可以减少找按钮和误触的成本。

物理按键监听依赖 `HAC` 容器和设备按键能力。普通浏览器无法按这种方式监听 Android 原生按键。

## 命令汇总

| 命令 | 类型 | 主要用途 |
| --- | --- | --- |
| 开始监听物理按键 | 异步 | 开始监听指定物理按键，并在按下时执行子命令 |
| 停止监听指定物理按键 | 普通命令 | 停止对某一个物理按键的监听 |
| 停止监听所有物理按键 | 普通命令 | 清理当前页面或流程中的全部物理按键监听 |

## 开始监听物理按键

【开始监听物理按键】是异步操作。命令执行后，APP 会开始监听指定物理按键。用户按下该按键时，会执行命令中配置的子命令。

可以把它理解为：

```text
进入需要按键操作的页面
-> 执行【开始监听物理按键】
-> 用户按下指定物理按键
-> HAC 捕获按键事件
-> 执行对应子命令
-> 页面根据业务结果继续处理
```

常见用法：

| 场景 | 按键触发动作 |
| --- | --- |
| 盘点或拣货 | 按下确认键后提交当前行或当前物料 |
| 巡检 | 按下快捷键后打开异常登记 |
| 收货 | 按下快捷键后聚焦数量输入或确认本箱 |
| 复核 | 按下快捷键后切换“通过 / 不通过”状态 |
| 设备调试 | 按下指定键后写入测试日志或显示当前设备状态 |

## 可监听的物理按键

【开始监听物理按键】中可以选择要监听的按键。插件目前提供的按键选项如下。

| 按键类别 | 可监听按键 |
| --- | --- |
| 系统与导航键 | 菜单键、返回键、主页键、搜索键 |
| 音量与电源键 | 音量加键、音量减键、电源键 |
| 电话与相机键 | 相机键、调用键、挂断键 |
| 方向与确认键 | 方向键上、方向键下、方向键左、方向键右、中央选择键 |
| 数字键 | 数字键0、数字键1、数字键2、数字键3、数字键4、数字键5、数字键6、数字键7、数字键8、数字键9 |
| 符号键 | 星号键、井号键 |

不同设备对实体按键的布局和上报可能不同。设计页面时，不要只按按键名称判断体验是否成立，还要在目标 PDA 或 Android 设备上确认用户能否方便按到该键，以及该键是否会和系统原有行为冲突。

## 是否覆盖按键原有操作

【开始监听物理按键】中可以配置“是否覆盖按键原有操作”。

如果勾选该选项，APP 会覆盖该按键在系统或 APP 中原本的行为。例如监听音量加键时，如果勾选“是否覆盖按键原有操作”，后续在 APP 中按下音量加键时，不会再增加音量，而是执行插件命令中配置的子命令。

| 配置 | 行为 |
| --- | --- |
| 不覆盖原有操作 | 按键原有行为仍可能继续发生，同时触发插件监听逻辑 |
| 覆盖原有操作 | 按键原有行为被拦截，优先执行插件配置的子命令 |

:::caution[谨慎覆盖系统按键]
覆盖音量键、返回键等常用按键前，要确认该页面确实需要独占按键行为。离开页面或任务结束时，应及时停止监听，避免影响其他页面或用户调整设备状态。
:::

建议只在明确的业务作业页覆盖按键原有操作，例如连续扫码、盘点确认、质检判定等。对于系统级按键，页面上最好给出可见状态，让用户知道当前按键已被业务流程接管。

## 停止监听指定物理按键

【停止监听指定物理按键】用于停止对某一个物理按键的监听。

适合在这些场景使用：

- 页面中只切换了某个按键的业务含义。
- 当前步骤结束，某个快捷键不再需要响应。
- 用户打开弹窗、拍照、签名或其他临时流程，需要暂停某个按键。
- 某个按键原本行为需要恢复，例如恢复音量加键的音量调节能力。

推荐流程：

```text
进入当前步骤
-> 开始监听指定物理按键
-> 按键触发子命令
-> 当前步骤完成
-> 执行【停止监听指定物理按键】
-> 进入下一步骤或恢复按键原有行为
```

如果同一个页面监听了多个物理按键，停止指定按键不会影响其他按键的监听。

## 停止监听所有物理按键

【停止监听所有物理按键】用于停止所有物理按键监听。

建议在这些时机执行：

- 离开当前页面。
- 当前业务流程完成。
- 用户切换到不需要物理按键的页面或模式。
- 页面发生异常，需要重置按键监听状态。
- 打开会占用用户注意力的系统能力，例如拍照、PDF 预览、拨打电话或 APP 内置设置页。

如果没有及时停止监听，可能出现旧页面继续响应按键、跨页面误触发、重复提交或覆盖系统按键行为没有恢复等问题。

## 推荐页面流程

物理按键监听通常应该和页面生命周期绑定。

```text
进入作业页面
-> 判断当前是否运行在 HAC 中
-> 初始化页面状态
-> 开始监听需要的物理按键
-> 用户按下按键
-> 子命令校验当前页面状态
-> 成功：执行提交、切换或跳转
-> 失败：提示失败原因，不改变关键状态
-> 离开页面或任务完成
-> 停止监听指定按键或停止监听所有物理按键
```

按键触发的子命令不应直接假设页面状态一定有效。建议先判断当前单据、物料、数量、焦点、弹窗状态或网络状态，再执行真正的业务动作。

## 异常处理

| 异常 | 可能原因 | 推荐处理 |
| --- | --- | --- |
| 按下物理按键无反应 | 未在 `HAC` 中运行、按键配置错误、监听未启动 | 提示检查运行环境和按键配置，并允许重新启动监听 |
| 按键触发了错误动作 | 页面重复注册监听、按键和子命令配置不一致 | 停止所有监听后重新注册，并记录当前页面状态 |
| 音量或返回等原有操作被拦截 | 勾选了“是否覆盖按键原有操作” | 在离开页面时停止监听，必要时提示用户当前按键被业务接管 |
| 连续触发多次子命令 | 用户长按、设备重复上报或子命令执行较慢 | 增加防抖、执行中锁定或重复提交校验 |
| 弹窗中仍响应旧按键 | 弹窗打开前未暂停监听 | 打开弹窗前停止指定按键，关闭后按需重新监听 |
| 离开页面后仍触发业务动作 | 未停止监听或监听器生命周期没有和页面绑定 | 在页面离开、任务完成和异常恢复时执行停止命令 |

## 页面设计注意点

- 物理按键适合高频动作，但页面上仍应保留可点击按钮，作为触屏备用入口。
- 页面应显示当前按键的业务含义，例如“确认键：提交当前项”。
- 覆盖系统按键时，要避免影响用户基本操作，尤其是音量键、返回键和电源相关按键。
- 按键触发提交类动作时，应做防重复提交处理。
- 如果按键用于危险或不可逆操作，应增加确认步骤，或要求按键只打开确认界面。
- 离开页面、打开弹窗、切换流程、任务完成和异常中断时，应清理不再需要的监听。
- 多个按键同时使用时，要避免不同按键触发相同子命令后造成状态竞争。

## 使用边界

物理按键监听属于 Android 设备能力调用，不是普通 Web 页面能力。使用时需要满足以下前提：

- 活字格应用运行在 `HAC` 中。
- 应用已安装并使用对应的 PDA / Android 交互命令插件。
- 当前设备存在可被监听的物理按键。
- 按键码、覆盖行为和设备厂商实现已经在真机上验证。

不同 PDA 厂商对物理按键、扫码键、音量键和自定义快捷键的上报方式可能不同。正式使用前，应在目标设备型号上做真机测试。

## 验收标准

1. 进入页面后，指定物理按键能触发预期子命令。
2. 勾选“是否覆盖按键原有操作”时，原有系统行为会按预期被拦截。
3. 不勾选覆盖时，页面行为和系统原有行为不会互相造成严重干扰。
4. 长按或连续按键不会造成重复提交、重复保存或状态错乱。
5. 打开弹窗、切换页面、任务完成和异常退出时，会停止对应按键监听。
6. 离开页面后，旧页面不会继续响应物理按键。
